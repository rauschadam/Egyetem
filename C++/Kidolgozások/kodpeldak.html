Bevezetés

1.1

Vizsgajegy kiszámítása

saját feladat

Számold ki a vizsgajegyet!

  1. elmélet: 12 pont, gyakorlat: 3-as
  2. elmélet: 9 pont, gyakorlat: 5-ös
  3. elmélet: 7 pont, gyakorlat: 5-ös
  4. elmélet: 14 pont, gyakorlat: 4-es
Megoldás
  1. 12 pont → 4-es; (4 + 3) / 2 = 3,5 → a gyakorlat (3) felé kerekítve: 3
  2. 9 pont → 2-es; (2 + 5) / 2 = 3,5 → a gyakorlat (5) felé: 4
  3. 7 pont → 1-es elmélet, így a vizsga nem sikerült (mindkét résznek legalább 2-esnek kell lennie)
  4. 14 pont → 5-ös; (5 + 4) / 2 = 4,5 → a gyakorlat (4) felé: 4
Részletes magyarázat
  • Ponthatárok: 8 alatt 1, 8–9: 2, 10–11: 3, 12–13: 4, 14-től 5.
  • Ha az átlag egész, nincs kerekítés; ha ,5-re jön ki, mindig a gyakorlati jegy felé kerekítünk, tehát a gyakorlat súlya nagyobb.
MegjegyzésA dián a képlet így szerepel: „elmélet + gyakorlat / 2.0”. C++-ban olvasva ez a precedencia miatt elmélet + (gyakorlat / 2.0) lenne (a / erősebben köt, ld. 4. előadás); a szándék nyilván (elmélet + gyakorlat) / 2.0.

Preprocesszor

2.1

Miért nem fordul le b.cpp?

dia: Példák

A két fájlt külön fordítjuk. Mi a hiba, és hogyan javítható?

// a.cpp:              // b.cpp:
void f( int i )        void g( int i )
{                      {
  // ...                 f( i );
}                      }
Megoldás

b.cpp fordításakor a fordító nem ismeri f-et:

b.cpp:3:8: error: 'f' was not declared in this scope

Javítás: b.cpp-ben a hívás előtt deklaráljuk a függvényt (void f( int );), vagy (jobb) a deklarációt egy a.h headerbe tesszük, és #include "a.h"-val emeljük be. Ezután mindkettőt lefordítjuk és összeszerkesztjük:

$ g++ -c a.cpp
$ g++ -c b.cpp
$ g++ a.o b.o -o prog
Részletes magyarázat
  • A fordító fordítási egységenként dolgozik: b.cpp fordításakor a.cpp tartalmáról nem tud semmit.
  • A deklaráció (void f( int );) csak azt ígéri, hogy van ilyen függvény; a fordító ebből ellenőrzi a hívást (paraméter típusa, száma).
  • A definíciót (a törzset) a linker keresi meg. Ha a.o-t kihagyjuk a szerkesztésből, a hiba már linkelési: „undefined reference to f(int)”.
  • Header nélkül minden hívó fájlba kézzel kellene beírni a deklarációt, és ha f paraméterei változnak, mindenhol javítani kellene.
2.2

A SQUARE makró

dia: Makrók

Mit ír ki a négy kiírás?

#define SQUARE( x ) x * x
std::cout << SQUARE( 5 );        // (1)
std::cout << SQUARE( 2 + 3 );    // (2)

#define SQUARE( x ) ((x) * (x))
std::cout << SQUARE( 2 + 3 );    // (3)
int i = 5;
std::cout << SQUARE( i++ );      // (4)
Megoldás
kifejtéseredmény
(1)5 * 525
(2)2 + 3 * 2 + 311 (nem 25!)
(3)((2 + 3) * (2 + 3))25
(4)((i++) * (i++))nem definiált (pl. 30 vagy 25), i kétszer nő

(A négy szám elválasztó nélkül kerül egymás után a kimenetre.)

Részletes magyarázat
  • A makró szövegcsere: a preprocesszor a paraméter szövegét bemásolja, nem számolja ki előre. A (2)-nél a * erősebben köt, mint a +.
  • A zárójelezett változat a precedencia-problémát megoldja, de a mellékhatásosat nem: az i++ szövegesen kétszer szerepel, és két szekvenciapont között kétszer módosítja i-t → nem definiált viselkedés.
  • A második #define SQUARE újradefiniálás; a g++ figyelmeztet („SQUARE redefined”). Szabályosan előtte #undef SQUARE kellene.
  • C++-os megoldás: inline int square( int x ) { return x * x; }: ez valódi függvény, a paraméter egyszer értékelődik ki, és van típusellenőrzés.
2.3

Include guard

dia: Include guard

Mi történik, ha egy fordítási egységbe (közvetve, két másik headeren keresztül) kétszer kerül be a complex.h, ha nincs benne include guard? És ha van?

// complex.h:
#ifndef COMPLEX__H
#define COMPLEX__H
class Complex
{
private:
  double re, im;
public:
  double abs();
};
#endif
Megoldás

Guard nélkül az osztálydefiníció kétszer szerepel a fordítási egységben → fordítási hiba:

error: redefinition of 'class Complex'

Guarddal: az első bemásoláskor COMPLEX__H még nem definiált, ezért a tartalom bekerül, és definiálódik a makró. A másodiknál az #ifndef hamis, így az egész #endif-ig kimarad → a definíció csak egyszer szerepel

Részletes magyarázat
  • Az include guard egy fordítási egységen belül véd. Különböző .cpp-kbe ugyanaz a header bekerülhet (és be is kell kerülnie), mert azokat külön fordítjuk.
  • #pragma once ugyanezt egy sorban csinálja; nem szabványos, de minden elterjedt fordító ismeri.
  • A makró nevének egyedinek kell lennie (szokás: fájlnév nagybetűvel).
MegjegyzésA dián a makró neve COMPLEX__H. A dupla aláhúzást tartalmazó azonosítók szigorúan véve fenntartottak (ld. 3. előadás, aláhúzásos azonosítók), ezért biztonságosabb a COMPLEX_H név.
2.4

Mire jó ez a header-részlet?

dia: C/C++ feltételes fordítás
#ifdef __cplusplus
extern "C" {
#endif
int add( int a, int b );
#ifdef __cplusplus
}
#endif
Megoldás

Ugyanazt a headert C-ből és C++-ból is be lehet emelni. C++ fordításkor (__cplusplus definiált) a deklaráció extern "C" { … } blokkba kerül, így a függvény C-s szerkesztésű lesz; C fordításkor a blokk nyitó és záró sora kimarad (a C nem ismeri az extern "C"-t).

Részletes magyarázat
  • A C++ fordító a szimbólumnevekbe belekódolja a névteret és a paramétertípusokat (name mangling, pl. _Z3addii); a C fordító nem (add).
  • Ha egy C-ben fordított add-ot C++-ból hívunk extern "C" nélkül, a linker _Z3addii-t keresne, és nem találná: undefined reference.
  • A __cplusplus egyike a fordító által előre definiált makróknak; a listát a g++ -dM -E -x c++ - < /dev/null írja ki.

Lexikális egységek

3.1

Fordítási hiba

dia: Fordítási hiba

Mi a hiba? Javítsd, és add meg, mit ír ki a javított függvény az f( 1, 5 ) hívásra!

#include <iostream>
void f( int a, int b )
{
  for( i = a; i <= b; ++i )
  {
    std::cout << i << ' ';
  }
}
Megoldás
ex.cpp:5:8: error: 'i' was not declared in this scope

Javítás: for( int i = a; i <= b; ++i ). Kimenet: 1 2 3 4 5 (a végén is van szóköz).

Részletes magyarázat
  • A ciklusváltozót deklarálni kell; a for fejében deklarált i csak a ciklusban látszik.
  • Ez hiba, nem figyelmeztetés: nem készül tárgykód.
  • A dián a ' ' görbe idézőjelekkel (’ ’) szerepel: ez csak a diakészítő program tipográfiája, a kódban egyenes ' kell.
3.2

Előjeles–előjel nélküli összehasonlítás

dia: Fordítási figyelmeztetés

Mit ír ki? Miért figyelmeztet a fordító?

int i = -2;
unsigned int j = 3;
if ( i < j )
{
  std::cout << "OK";
}
else
{
  std::cout << "WTF?";
}
Megoldás

Kiírás: WTF?

warning: comparison between signed and unsigned integer expressions [-Wsign-compare]
Részletes magyarázat
  • Ha egy int és egy unsigned int egy műveletben találkozik, az int unsigned int-té konvertálódik (szokásos aritmetikai konverziók).
  • −2 kettes komplemensben 0xFFFFFFFE, előjel nélkül olvasva 4 294 967 294 (32 bites int-nél). Ez nem kisebb 3-nál.
  • Javítás: azonos előjelű típusokkal hasonlítsunk (pl. if ( i < static_cast<int>( j ) )), vagy előbb nézzük meg, hogy i < 0.
  • Tipikus előfordulás: for( int k = 0; k < v.size(); ++k ): a size() előjel nélküli.
3.3

VLA: változó hosszúságú tömb

dia: Fordítási figyelmeztetés

Szabályos C++ ez? Mi a gond még vele?

int f( int i )
{
  int x[ i ];
  return x[ 0 ] + x[ 1 ];
}
Megoldás
warning: ISO C++ forbids variable length array 'x' [-Wvla]

Nem szabványos: C++-ban a tömbméretnek fordítási idejű konstansnak kell lennie; a g++ csak bővítményként fogadja el, -pedantic-kal figyelmeztet.

Részletes magyarázat
  • A VLA C99-ben szabályos, onnan „szivárgott át” a g++-ba.
  • További hibák: a tömbelemek inicializálatlanok, így x[ 0 ] + x[ 1 ] szemét; ha i < 2, a tömbön kívülre olvasunk (nem definiált viselkedés); nagy i-re a verem túlcsordulhat.
  • C++-os megoldás: std::vector<int> x( i ); (a heapen foglal, az elemek 0-ra inicializálódnak).
3.4

Melyik módosítás szabályos?

dia: Konstans szövegliterálok típusa

Melyik kommentben lévő értékadás fordul le, és melyik fut helyesen?

const char a[] = "Hello"; // a[ 0 ] = 'h';
char b[] = "Hello";       // b[ 1 ] = 'a';
const char* p = ":-)";    // p[ 2 ] = 'D';
char* q = "WTF?";         // q[ 3 ] = '!';
Megoldás
lefordul?fut?
a[ 0 ] = 'h';nem: a elemei const-ok–
b[ 1 ] = 'a';igenigen: b saját tömb, a literál másolata → "Hallo"
p[ 2 ] = 'D';nem: p const char-ra mutat–
char* q = "WTF?"; + q[ 3 ] = '!';igen, figyelmeztetésselnem definiált: a literált írnánk, ami csak olvasható memóriában van → tipikusan Segmentation fault
Részletes magyarázat
  • A literál típusa const char[ N ]; a statikus tárterületen, gyakran csak olvasható lapon van.
  • char b[] = "Hello"; egy új, 6 elemű tömböt hoz létre a veremen, és belemásolja a literált: ez szabadon írható.
  • const char* p = ":-)"; nem másol: p magára a literálra mutat; a const miatt a fordító nem enged írni.
  • char* q = "WTF?"; a const elhagyása: C-kompatibilitás miatt C++98-ban még elfogadott volt (elavultként), C++11 óta nem szabályos; a g++ figyelmeztet:
warning: deprecated conversion from string constant to 'char*' [-Wwrite-strings]
3.5

sizeof és strlen

dia: Stringek hossza

Mit ír ki a program 64 bites rendszeren?

#include <iostream>
#include <cstring>
int main()
{
  char h[] = "Hello";
  char w[] = "World";
  char *p = h;
  std::cout << sizeof( h ) << ' ' << std::strlen( h ) << std::endl;
  std::cout << sizeof( w ) << ' ' << std::strlen( w ) << std::endl;
  std::cout << sizeof( p ) << std::endl;
  h[ 2 ] = '\0';
  std::cout << sizeof( h ) << ' ' << std::strlen( h ) << std::endl;
  std::cout << sizeof( p ) << std::endl;
  p = "It is a very very long string";
  std::cout << sizeof( p ) << std::endl;
}
Megoldás
6 5
6 5
8
6 2
8
8
Részletes magyarázat
  • sizeof( h ): a tömb mérete bájtban, a lezáró '\0'-val: 5 + 1 = 6. Fordítási időben dől el, ezért a h[ 2 ] = '\0' után sem változik.
  • strlen( h ): az első '\0'-ig számol: először 5, a h[ 2 ] = '\0' után 2 ("He").
  • sizeof( p ): p egy pointer, a mérete a pointer mérete (64 biten 8, 32 biten 4), függetlenül attól, mire mutat: a hosszú szövegnél is 8.
  • A dián a #include <cstring> hiányzik; a std::strlen ehhez a headerhez tartozik (néha az <iostream> véletlenül behúzza, de erre nem szabad építeni).
  • A p = "It is …"; sor ismét const-ot hagy el (char*-ba literál), erre a fordító figyelmeztet.
3.6

Szövegek összehasonlítása

dia: Szövegtartalmak összehasonlítása

Mit írnak ki a változatok?

const char a[] = "Hello";
char b[] = "Hello";
if ( a == b )                       // (1)
  std::cout << "OK";
else
  std::cout << "WTF?";

if ( 0 == std::strcmp( a, b ) )     // (2)
  std::cout << "OK";
else
  std::cout << "WTF?";
Megoldás

(1): WTF?, (2): OK

Részletes magyarázat
  • Az == két tömbnél a tömbök első elemének címét hasonlítja össze (a tömb pointerré konvertálódik). a és b két külön tömb, a címük biztosan különbözik.
  • std::strcmp karakterenként hasonlít, és 0-t ad, ha a tartalom azonos (negatívat/pozitívat, ha az első kisebb/nagyobb).
  • A 0 == … „Yoda-sorrend” miatt egy elírt = fordítási hibát okozna.
  • Újabb g++ már erre is figyelmeztet (-Warray-compare). std::string-nél az == tartalmat hasonlít, ott ez a csapda nincs.

4.2

Kifejezések eredménye és mellékhatása

dia: Példák

Legyen int x = 1, y = 3, a = 2, b = 4;. Mindegyik sort ebből az állapotból kiindulva értékeld ki: mi az eredmény, és mi a mellékhatás?

7+x

12 / 5

Megoldás
kifejezéseredménymellékhatás

x++1 (a régi érték)x = 2

4.3

Precedencia és kötés

dia: Kiértékelés, példa / AST / Kötés

Mennyi 1+2*3+4? Rajzold fel a szintaxisfáját! Hogyan zárójelezi a fordító az x = a + b + c + d; és az a = b = c = d = x; sorokat?

Megoldás

11

     +
   /   \
  +     4
 / \
1   *
   / \
  2   3
  • x = a + b + c + d; → x = (((a + b) + c) + d); (a + balról köt)
  • a = b = c = d = x; → a = (b = (c = (d = x))); (az = jobbról köt)
Részletes magyarázat
  • A precedencia dönti el, melyik operátor köt erősebben: a * előbb, mint a +.
  • Azonos precedenciánál a kötés (asszociativitás) dönt. A fa gyökerében az utoljára elvégzett művelet áll: itt a második +.
  • Az értékadás jobbról köt, és értéke az új érték, ezért a láncolt értékadás mind a négy változónak x-et adja.
  • Figyelem: a precedencia és a kötés a zárójelezést határozza meg, nem a kiértékelési sorrendet! f() + g() esetén nem garantált, hogy f hívódik előbb.
4.4

Prefix és postfix inkrementálás

dia: Inkrementálás, dekrementálás
int i = 1;
std::cout << ++i;   // (1)

int j = 1;
std::cout << j++;   // (2)
std::cout << j;     // (3)
Megoldás

(1): 2, (2): 1, (3): 2

Részletes magyarázat
  • Mellékhatás mindkét esetben: a változó eggyel nő.
  • Eredmény: ++i az új értéket, j++ a régit adja vissza.
  • A for( int i = 0; i < n; ++i ) fejlécben az eredményt nem használjuk, ott mindegy; objektumoknál (iterátor) a ++i hatékonyabb, mert a postfix változatnak másolatot kell készítenie a régi értékről.
4.5

Értékadás a feltételben

dia: Értékadás – mit ír ki az alábbi kódrészlet?

Mit ír ki, és mennyi lesz x értéke?

if ( x = 0 )
{
  std::cout << 'A' << std::endl;
}
if ( x = 4 )
{
  std::cout << 'B' << std::endl;
}
Megoldás

Kimenet: B, és x == 4.

Részletes magyarázat
  • x = 0 értékadás: x 0 lesz, a kifejezés értéke 0 → hamis, az A nem íródik ki.
  • x = 4: értéke 4 → igaz (minden nem nulla érték igaz), kiíródik a B.
  • A -Wall figyelmeztet: „suggest parentheses around assignment used as truth value”. Ha tényleg értékadást akarunk a feltételben, dupla zárójellel jelezzük: if ( ( x = f() ) ).
4.6

f() == g() == h()

dia: Példa (szekvenciapontok)

Mit ír ki?

bool f() { std::cout << 'f'; return false; }
bool g() { std::cout << 'g'; return true; }
bool h() { std::cout << 'h'; return false; }

if ( f() == g() == h() )
  std::cout << ":-)";
else
  std::cout << ":-(";
Megoldás

A feltétel igaz, így a vége :-). Az f, g, h betűk sorrendje nem meghatározott; a g++ tipikusan fgh:-)-t ír ki.

Részletes magyarázat
  • Az == balról köt: ( f() == g() ) == h().
  • f() == g(): false == true → false. Utána false == h(): false == false → true.
  • A == operandusainak kiértékelési sorrendje nincs rögzítve, és nincs köztük szekvenciapont: a fordító hívhatja előbb h-t, vagy g-t f előtt. Az eredmény ettől nem függ, csak a kiírt betűk sorrendje.
  • A tanulság: ne írjunk olyan kifejezést, amelynek eredménye a mellékhatások sorrendjén múlik. A a == b == c ráadásul nem azt jelenti, hogy „mind egyenlő”.
4.7

v[ i ] = i++

dia: Példa (szekvenciapontok)

Mi a gond ezzel a ciklussal?

const int s = 5;
int v[ s ];
for( int i = 0; i < s; )
{
  v[ i ] = i++;
}
Megoldás

Az i egy kifejezésen belül módosul (i++) és olvasódik (v[ i ]) is, köztük nincs szekvenciapont: C++98-ban (a diák -ansi módjában) nem definiált viselkedés.

Részletes magyarázat
  • Ha a fordító előbb a bal oldalt értékeli ki: v[0]=0, v[1]=1, … (amire a szerző gondolt). Ha előbb a jobb oldalt: v[1]=0, v[2]=1, …, v[5]=4: ez már a tömbön kívülre ír, v[0] pedig kimarad.
  • C++17 óta az értékadás jobb oldala garantáltan a bal oldal előtt értékelődik ki: így éppen a második, hibás eset a kötelező (v[5]-be is ír).
  • Helyesen: v[ i ] = i; ++i;, vagy egyszerűen for( int i = 0; i < s; ++i ) v[ i ] = i;.
4.8

Vessző operátor és függvényargumentumok

dia: Szekvenciapontok

Mennyi d, és mit ír ki g()?

void f( int a )        { std::cout << a << ' ' << 1; }
void f( int a, int b ) { std::cout << a << ' ' << b << ' ' << 2; }

void g()
{
  double d = (2,5);
  int x = 2;
  f( x++, x++ );
  f( ( x++, x++ ) );
}
Megoldás
  • d = 5 (nem 2,5!)
  • f( x++, x++ ) a kétparaméteres f-et hívja. C++98–14-ben nem definiált viselkedés; C++17 óta az argumentumok sorrendje csak nem meghatározott, így 2 3 2 vagy 3 2 2 (a g++ jellemzően jobbról balra értékel, így 3 2 2). Utána x = 4.
  • f( ( x++, x++ ) ) az egyparaméteres f-et hívja: az első x++ után x = 5, a második x++ értéke 5 (utána x = 6) → 5 1.

Mivel nincs sortörés, a teljes kimenet pl.: 3 2 25 1

Részletes magyarázat
  • A (2,5) zárójelben a vessző operátor: kiértékeli a 2-t, eldobja, az eredmény az 5. (Magyar tizedesvessző-szokás itt nem működik!) A g++ figyelmeztet: „left operand of comma operator has no effect”.
  • Függvényhívásban a vessző elválasztó, nem operátor, nincs utána szekvenciapont. A két x++ ugyanazt a változót módosítja: régi szabvány szerint ez UB.
  • A dupla zárójel ( x++, x++ ) egyetlen argumentum, benne vessző operátor, ami szekvenciapont: előbb az első x++ teljesen lezajlik, utána a második.
  • A két f túlterhelés (overload): a fordító az argumentumok száma alapján választ.
4.9

Szekvenciapontok, kérdések

dia: Szekvenciapontok, kérdések

Az előző f (kiírja f, false-t ad) és g (kiírja g, true-t ad) függvényekkel mit ír ki és mi a feltétel értéke?

if ( f() || g() ) // (2)
if ( f(), g() )   // (3)
if ( g(), f() )   // (4)
Megoldás
kiírásfeltétel
(1)fhamis
(2)fgigaz
(3)fgigaz
(4)gfhamis
Részletes magyarázat
  • (1) && lusta: f() hamis, így az eredmény biztosan hamis, g() meg sem hívódik.
  • (2) ||: f() hamis, ezért ki kell értékelni g()-t is, ami igaz.
  • (3)–(4) vessző operátor: mindkét oldal kiértékelődik, balról jobbra (szekvenciapont), az eredmény a jobb oldal értéke.
  • Itt a sorrend mindenhol garantált, mert &&, || és a vessző operátor után szekvenciapont van (szemben az előző ==-s példával).

5.11

Kivétel és szivárgás

dia: Problémák / RAII

Mi a gond ezzel a kóddal? Írd át RAII-val!

void f( int i )
{
  int *p = new int[ i ];
  complex* c = new complex( 1.2, 3.4 );
  f( ... );
  g( ... );
  // ...
  delete [] p;
  delete c;
}
Megoldás

Ha f( … ) vagy g( … ) kivételt dob (vagy a kódba később egy korai return kerül), a vezérlés nem ér el a delete-ekig → memóriaszivárgás. RAII-val:

void f( int i )
{
  std::vector<int> p( i );       // a vector destruktora felszabadít
  complex c( 1.2, 3.4 );         // egyszerűen a veremen
  f( ... );
  g( ... );
}                                // minden automatikusan megszűnik
Részletes magyarázat
  • A lokális objektumok destruktora minden kilépéskor lefut (normál visszatérés, return, kivétel).
  • A complex-et semmi nem indokolja a heapen: felhasználói típusú objektum is lehet a vermen.
  • Ha mégis heap kell egy objektumnak: std::unique_ptr<complex> c( new complex( 1.2, 3.4 ) ); (C++14-től std::make_unique).

  • (3)–(4) problémája: std::cout << answer( "Hogy vagy?" ) << std::endl << answer( "Biztos?" ) << std::endl;. Régi szabvány szerint a fordító előbb mindkét answer-t meghívhatja, és csak utána ír ki: ilyenkor mindkét pointer ugyanarra a tömbre mutat, így a második választ írja ki kétszer. (C++17 óta a << lánc balról jobbra értékelődik ki, így ez a konkrét kiírás jó lenne, de pl. const char* a = answer( … ); const char* b = answer( … ); után a és b ugyanazt mutatja.)
  • (4) a lokális statikus élettartam miatt működik: a tömb a program végéig él.
  • (7): a visszaadás nem drága: a fordító RVO-val a hívó helyén hozza létre a stringet, vagy (C++11 óta) mozgatja.
MegjegyzésA dián a (7)-es változatban ans.getline( std::cin ); szerepel. Ilyen tagfüggvénye az std::string-nek nincs; a helyes alak a szabad függvény: std::getline( std::cin, ans ); (itt így szerepel).
