Bevezetés

MegjegyzésSzámonkérés és vizsga

Félév közben a gyakorlaton 3 db +/− jár, és van egy opcionális beadandó (code review-val). A vizsga két részből áll:

  • elmélet: 15 tesztkérdés, kb. 30–45 perc;
  • gyakorlat: egy 3 órás programozási feladat.
elméleti pont< 88–910–1112–1314–
jegy12345

Vizsgajegy = (elmélet + gyakorlat) / 2, ha mindkettő legalább 2-es; ha az átlag nem egész, a gyakorlati jegy felé kerekítünk. Pl. elmélet 3, gyakorlat 4 → 3,5 → 4; elmélet 4, gyakorlat 3 → 3,5 → 3.

dia: „Számonkérés”

  • 3 darab +/- (gyakorlat)
  • Opcionális beadandó, code review
  • Vizsga: Elmélet: 15 tesztkérdés, kb. 30-45 perc; +/- szerepe
  • Elmélet értékelése: 8 pont alatt: 1; 8-9 pont: 2; 10-11 pont: 3; 12-13 pont: 4; 14- pont: 5
  • Vizsga: Gyakorlati feladat, 3 óra
  • Vizsgajegy: elmélet + gyakorlat / 2.0, ha az elmélet és a gyakorlat is legalább 2-es
  • Vizsgajegy: gyakorlat felé kerekítve, ha az átlag nem egész szám

FogalomProgramozási nyelvek osztályozása

Egy nyelvet több szempont szerint jellemezhetünk:

  • általános célú (C++, Java) vs. domain-specifikus (SQL, HTML, regex: egy szűk feladatra);
  • alacsony szintű (assembly, közel a géphez) vs. magas szintű (absztrakciók, a gép részletei rejtve);
  • fordított (C++ → gépi kód) vs. interpretált (Python: soronként értelmezi egy program) vs. bytecode (Java: köztes kód + virtuális gép);
  • a típusrendszer sajátosságai (statikus/dinamikus, erős/gyenge);
  • a támogatott programozási paradigmák.

dia: „Osztályozás”

  • Általános célú vs. Domain-specifikus
  • Alacsony-szintű vs. Magas-szintű
  • Fordított vs. interpretált vs. bytecode
  • Típusrendszeri sajátosságok
  • Programozási paradigmák
FogalomProgramozási paradigma

A paradigma egy gondolkodásmód és eszköztár: hogyan bontsunk egy összetett problémát kisebb részekre (dekompozíció), és milyen nyelvi eszközökkel, bevált tudással (know-how) rakjuk össze a megoldást. Pl. OO-ban objektumokra bontunk, funkcionálisan függvényekre.

dia: „Programozási paradigmák fogalma”

  • Összetett problémák
  • Dekompozíció
  • Eszközök
  • Know-how
EszközA paradigmák fajtái

A fő ágak:

  • imperatív (megmondjuk, hogyan számoljon, lépésenként): procedurális, strukturált, objektum-orientált;
  • deklaratív (megmondjuk, mit akarunk): funkcionális (Haskell), logikai (Prolog);
  • generikus (típustól független kód, C++-ban template-ek, STL).

További, ritkább irányok: generatív technológiák, aspektus-orientált, metaprogramozás, intencionális és feature-orientált programozás.

dia: „Programozási paradigmák”

  • Imperatív: Procedurális, Strukturált, Objektum-orientált
  • Deklaratív: Funkcionális, Logikai
  • Generikus
  • Generatív technológiák
  • Aspektus-orientált
  • Metaprogramozás
  • Intencionális
  • Feature-orientált
FogalomA C++ multiparadigmás nyelv

A C++ nem kényszerít egyetlen stílusra: ugyanabban a programban használhatunk

  • procedurális kódot (a C-től örökölt alapok: függvények, ciklusok),
  • objektum-orientált kódot (osztályok, öröklődés, virtuális függvények),
  • generikus kódot (template-ek, a szabványkönyvtár STL része),
  • metaprogramozást (a fordító fordítási időben számol, template-ekkel).

dia: „C++: multiparadigmás nyelv”

  • Procedurális alapok (C)
  • Objektum-orientáltság
  • Generikus programozás (STL)
  • Metaprogramozás

SzabályA C++ alapkoncepciói
  • C-kompatibilitás: (majdnem) minden C program C++ program is; ezért él tovább sok C-s csapda.
  • Jobb eszközök a C-s problémákra: pl. std::string a char* helyett, const a #define helyett, referenciák, RAII.
  • Hatékonyság + magas szintű konstrukciók egyszerre.
  • A fordító a barátunk: minél több hibát fordítási időben fogjon meg (típusok, figyelmeztetések).
  • „Ne fizessünk azért, amit nem kérünk” (zero-overhead): ami nyelvi eszközt nem használunk, az nem lassít (pl. nincs automatikus szemétgyűjtés vagy indexhatár-ellenőrzés).
  • Általános, hatékony és átfogó szabványkönyvtár.

dia: „A C++ alapkoncepciói”

Preprocesszor

FogalomFordítás, fordítóprogram

A processzor csak gépi kódot ért, a C++ forrást előbb le kell fordítani (pl. g++-szal). A fordító közben ellenőriz (típusok, deklarációk): ez növeli az esélyét, hogy a program helyes, de nem garantálja. Emellett optimalizálhat is (gyorsabb kódot generál).

dia: „Bevezetés”

  • A processzor csak a gépi kódot érti, pl. C/C++ kódot nem tud egyből végrehajtani.
  • Futtatás előtt a C/C++ programokat le kell fordítani.
  • Fordítóprogramot használunk (pl. g++).
  • Fordítóprogramok a programok bizonyos tulajdonságait ellenőrzik, ez növeli a program helyességének esélyét, de nem garantálja azt.
  • A fordítóprogramok optimalizál(hat)ják a kódot.
FogalomA fordítás lépései
  1. Preprocesszálás – szövegszintű előfeldolgozás (#include, #define …): g++ -E a.cpp mutatja az eredményt.
  2. Nyelvi fordítás (compiler) – a kifejtett C++ szövegből tárgykód (.o): g++ -c a.cpp.
  3. Összeszerkesztés (linker) – a tárgykódokból és könyvtárakból futtatható program: g++ a.o b.o -o prog.

A g++ a.cpp mindhármat egyben elvégzi. A -save-temps kapcsoló megtartja a köztes fájlokat (.ii preprocesszált, .s assembly, .o tárgykód).

dia: „Lépések”

  1. Preprocesszálási fázis (preprocessor)
  2. Nyelvi fordítás (compiler)
  3. Összeszerkesztés (linker)
FogalomFordítási egység és header fájl

Fordítási egység = egy .cpp fájl a preprocesszálás után (minden #include bemásolva). A fordító egyenként, egymástól függetlenül fordítja őket. A header fájlok (.h) nem önálló egységek: arra valók, hogy közös deklarációkat több .cpp bemásolhasson.

dia: „Forrás file-ok”

  • Fordítási egység: .cpp
  • Header file-ok
FogalomModularizálás

Nagyobb programot több fájlba szervezünk: így többen dolgozhatnak rajta, könnyebb karbantartani, és módosításkor csak a megváltozott fájlokat kell újrafordítani (ezt automatizálja a make egy Makefile alapján).

dia: „Modularizálás”

  • Egy programot általában több (sok) file-ban írunk meg, modularizáljuk
  • Csapatmunka növelése
  • Karbantarthatóság
  • Csak a szükséges file-okat fordítsuk újra (make, Makefile)
FogalomPreprocesszor

Szövegátalakító eszköz, ami a fordító előtt fut: fájlokat másol be, szövegrészeket kivág vagy benntart, és keres-cserél. Nem ismeri a C++-t (bármilyen szövegen működne), ezért nem tud típusokról, hatókörről. Csak indokolt esetben használjuk; ahol lehet, helyette C++ nyelvi eszköz kell (const, inline függvény, template). Makrónév konvenció: CSUPA_NAGYBETŰ.

dia: „Alapok”

  • Szövegátalakító eszköz
  • File tartalmának beillesztése
  • Szövegrészek kivágása/benntartása
  • Search & replace
  • Nyelv-független eszköz, nem foglalkozik azzal, hogy C/C++ kódot dolgoz-e fel
  • Csak a szükséges esetekben használjuk
  • Automatizálás bizonyos esetekben
  • C++ nyelvi konstrukciók
  • Azonosítók konvenciója
FogalomDirektíva

A #-tel kezdődő sor a preprocesszornak szól. Nem utasítás: nem fut le a programban, nincs a végén ;, hanem fordítás előtt átalakítja a forrásszöveget.

dia: „Direktívák”

  • #
  • Szövegátalakítás, nem végrehajtás
  • Direktívák, nem utasítások
EszközAlapvető direktívák
direktívamit csinál
#include <iostream>a rendszer/szabványos header bemásolása (a rendszerkönyvtárakban keresi)
#include "a.h"saját header bemásolása (először az aktuális könyvtárban keresi)
#define N 20makró: ezután minden N szövegesen 20-ra cserélődik
#undef Na makró törlése
#ifdef X / #ifndef Xa következő rész csak akkor marad, ha X definiált / nem definiált
#if #elif #else #endiffeltételes fordítás konstans kifejezés alapján

dia: „Alapvető direktívák”

  • #include
  • #define, #undef
  • #ifdef, #ifndef,
  • #if, #else, #elif, #endif
SzabályDeklaráció kell a használat előtt

A fordító fordítási egységenként dolgozik: b.cpp fordításakor nem lát bele a.cpp-be. Ha b.cpp hívja f-et, előtte kell egy deklaráció (void f( int );), különben: „'f' was not declared in this scope”. A deklaráció csak megígéri, hogy f létezik; a definíciót (a függvénytörzset) majd a linker keresi meg a.o-ban.

// a.cpp:                 // b.cpp:
void f( int i )           void f( int );   // deklaráció
{                         void g( int i )
  // ...                  {
}                           f( i );        // lefordul
                          }

dia: „Példák”

A deklaráció nélküli b.cpp-re: b.cpp:3:8: error: 'f' was not declared in this scope. A void f( int ); deklarációval kiegészítve: „Lefordul”.

FogalomHeader fájl

Ha sok .cpp hív sok függvényt, a deklarációkat kézzel bemásolgatni karbantarthatatlan. Ezért a deklarációkat egy header fájlba (a.h) írjuk, és a preprocesszor #include "a.h"-val automatikusan bemásolja oda, ahol kell.

// a.h:            // b.cpp:
void f( int );     #include "a.h"
                   void g( int i ) { f( i ); }

dia: „Header file-ok”

  • Sok fordítási egység
  • Sok függvény
  • Karbantartás
  • Automatizálás
  • Függvények deklarációi header file-okban
  • Header file-ok automatikus bemásolása preprocesszorral
PéldaKonstans #define-nal

Tömbméret paraméterezése: #define N 20, aztán int x[ N ]; és for( int i = 0; i < N; ++i ). Ha a méret változik, egy helyen írjuk át. Modern C++-ban inkább const int N = 20; (vagy constexpr): ennek van típusa és hatóköre, a makrónak nincs.

dia: „Tömb méretének paraméterezése”

#define N 20
#define M 30
int x[ N ];
int y[ N ];
int z[ M ];
for( int i = 0; i < N; ++i )
{
  y[ i ] = x[ i ];
}
CsapdaFüggvényszerű makró

A makró szövegcsere, nem függvényhívás: a paraméter helyére a megadott szöveg kerül, kiértékelés nélkül.

  • #define SQUARE( x ) x * x → SQUARE( 2 + 3 ) = 2 + 3 * 2 + 3 = 11, nem 25.
  • Javítás: mindent zárójelezünk: #define SQUARE( x ) ((x) * (x)) → 25.
  • De SQUARE( i++ ) = ((i++) * (i++)): i kétszer nő, ráadásul nem definiált viselkedés.

Megoldás C++-ban: inline int square( int x ) { return x * x; } (vagy template).

dia: „Makrók”

#define SQUARE( x ) x * x
std::cout << SQUARE( 5 );
std::cout << SQUARE( 2 + 3 );

#define SQUARE( x ) ((x) * (x))
std::cout << SQUARE( 2 + 3 );
int i = 5;
std::cout << SQUARE( i++ );
FogalomInclude guard, #pragma once

Ha egy header (pl. egy osztálydefiníció) kétszer kerül be ugyanabba a fordítási egységbe (közvetve, más headereken át), a fordító „redefinition of class Complex” hibát ad. Az include guard ezt akadályozza meg: az első bemásoláskor definiál egy makrót, a másodiknál már kihagyja a tartalmat. Ugyanezt egy sorban: #pragma once (nem szabványos, de minden fordító ismeri).

#ifndef COMPLEX_H
#define COMPLEX_H
class Complex { /* ... */ };
#endif

dia: „Include guard”

  • Osztályok megosztása fordítási egységek között
  • Include guard
  • Pragma once
// complex.h:
#ifndef COMPLEX__H
#define COMPLEX__H
class Complex
{
private:
  double re, im;
public:
  double abs();
  // ...
};
#endif
FogalomFeltételes fordítás

Az #ifdef/#if családdal a fordítás előtt dől el, mely kódrészek maradnak meg (pl. platformfüggő kód, debug kiírások). A fordító előre definiál makrókat; ezeket kilistázza: g++ -dM -E -x c++ - < /dev/null. Pl. __cplusplus csak C++ fordításnál definiált, így egy header C-ből és C++-ból is használható:

#ifdef __cplusplus
extern "C" {
#endif
// C függvények deklarációi
#ifdef __cplusplus
}
#endif

Az extern "C" kikapcsolja a C++ névdekorálást (name mangling), így a C-ben fordított függvények megtalálhatók.

dia: „Feltételes fordítás – demo / C/C++ feltételes fordítás”

g++ -dM -E -x c++ - < /dev/null

#ifdef __cplusplus
extern "C" {
#endif
// ...
#ifdef __cplusplus
}
#endif
FogalomFordítás és futtatás más nyelvekben
  • Interpretált nyelv (pl. Python, shell): nincs előzetes gépi kódra fordítás, egy értelmező program futtatja a forrást.
  • Bytecode (pl. Java, C#): a fordító egy köztes, gépfüggetlen kódot készít, ezt egy virtuális gép (JVM) futtatja.
  • JIT (just-in-time) compiler: a virtuális gép futás közben a gyakran futó részeket gépi kódra fordítja.

dia: „Fordítás, futtatás”

  • Interpretált nyelvek
  • Byte code
  • JIT compiler

Lexikális egységek

FogalomA nyelvi fordítás feladatai

A compiler a preprocesszált C++ kódból „gépi nyelvet” (tárgykódot) készít, közben ellenőriz (hibák), figyelmeztet (gyanús, de szabályos kód), optimalizál, és statikus elemzéssel hibákat kereshet.

dia: „Nyelvi fordítás”

  • C++ → „gépi nyelv”
  • Fordítási ellenőrzések
  • Fordítási figyelmeztetések
  • Optimalizációk
  • (Hibakeresés statikus elemzéssel)
FogalomFordítási hiba és figyelmeztetés

Hiba (error): a kód nem felel meg a nyelvnek, nem készül program (pl. deklarálatlan változó: „'i' was not declared in this scope”). Figyelmeztetés (warning): a kód szabályos, lefordul, de gyanús, valószínűleg hibás (pl. signed–unsigned összehasonlítás). A figyelmeztetéseket komolyan kell venni.

dia: „Fordítási hiba / Fordítási figyelmeztetés”

$ g++ -c -W -Wall -pedantic -ansi ex.cpp
ex.cpp:5:8: error: 'i' was not declared in this scope
$ g++ -c -W -Wall -pedantic -ansi warn.cpp
warn.cpp:7:10: warning: comparison between signed and unsigned integer expressions [-Wsign-compare]
EszközA g++ kapcsolói az előadásokon
kapcsolójelentés
-W -Wall(majdnem) minden hasznos figyelmeztetés bekapcsolása (-W = -Wextra)
-pedanticszigorúan a szabványt kéri számon, a g++-bővítményekre (pl. VLA) is figyelmeztet
-ansiC++-ban a C++98 szabvány szerinti fordítás (= -std=c++98)
-ccsak fordít (.o), nem szerkeszt
-Ecsak preprocesszál, az eredményt kiírja

dia: „Fordítási hiba (parancssor)”

g++ -c -W -Wall -pedantic -ansi ex.cpp, g++ -W -Wall -pedantic -ansi -save-temps -O0 af.cpp, … -O3 af.cpp

CsapdaElőjeles és előjel nélküli összehasonlítás

int i = -2; unsigned int j = 3; esetén i < j hamis! Vegyes összehasonlításnál az int átkonvertálódik unsigned-dá, és −2-ből egy óriási pozitív szám lesz (32 bites int-nél 4294967294). A program „WTF?”-ot ír ki; a fordító -Wsign-compare figyelmeztetést ad.

dia: „Fordítási figyelmeztetés”

int i = -2;
unsigned int j = 3;
if ( i < j )
{
  std::cout << "OK";
}
else
{
  std::cout << "WTF?";
}
CsapdaVáltozó hosszúságú tömb (VLA)

int x[ i ];, ahol i futás közben dől el: ez C99-ben szabályos, szabványos C++-ban nem (a tömbméretnek fordítási időben ismertnek kell lennie). A g++ bővítményként elfogadja, -pedantic-kal figyelmeztet: „ISO C++ forbids variable length array”. Helyette: std::vector<int> x( i );.

dia: „Fordítási figyelmeztetés”

int f( int i )
{
  int x[ i ];
  return x[ 0 ] + x[ 1 ];
}
FogalomStatikus elemzés

A forráskód vizsgálata futtatás nélkül, tipikus hibaminták után kutatva (pl. inicializálatlan változó, null pointer, memóriaszivárgás). Eszközök: maga a fordító figyelmeztetései, clang-tidy, cppcheck, Clang Static Analyzer.

dia: „Statikus elemzés”

A dián csak a cím és egy kép szerepel; a „Nyelvi fordítás” listájában: „(Hibakeresés statikus elemzéssel)”.

FogalomOptimalizáció

A fordító a jelentést megtartva gyorsabb/kisebb kódot generálhat. Az array_fill (6 elemet nulláz ciklusban) -O0-val szó szerinti ciklus lesz az assemblyben; -O3-mal a ciklus eltűnhet, helyette néhány nagy (vektoros) tárolás. A különbséget a -save-temps által megtartott .s fájlban láthatjuk.

dia: „Optimalizációk”

// af.cpp:
void array_fill( int* p )
{
  for( int i = 0; i < 6; ++i )
  {
    p[ i ] = 0;
  }
}
FogalomLexikális elemek

FogalomSzekvenciapont

A kiértékelés egy olyan pontja, ahol minden addigi kiértékelés és mellékhatás garantáltan befejeződött. Két szekvenciapont között a fordító szabadon választhat sorrendet. Láthatóság és memóriamodell

FogalomLáthatóság (hatókör, scope)

Egy név láthatósága az a programrész, ahol a nevet használhatjuk. Blokkban deklarált (lokális) név a deklarációjától a blokk végéig látszik. Pl. az if blokkjában deklarált t a blokk után már nem érhető el. (C vs. C++: a régi C-ben a deklarációk csak a blokk elején állhattak, C++-ban bárhol.)

dia: „Láthatóság fogalma”

void f()
{
  int y = 1;
  int x;
  std::cin >> x;
  if ( x > 10 )
  {
    ++x;
    int t = y;   // t innentől a blokk végéig látszik
    ++y;
  }
  ++x;
  ++y;
}
FogalomLáthatóság, élettartam, memóriamodell

Három külön kérdés: láthatóság – hol hivatkozhatunk a névre (fordítási idejű, a szövegre vonatkozik); élettartam – mikor létezik az objektum futás közben; memóriamodell – hol tárolódik (verem, statikus terület, heap). Pl. egy lokális static változó csak a függvényben látszik, de a program végéig él.

dia: „Fogalmak”

  • Élettartam
  • Memória modell
  • Láthatósági szabályok
SzabályÚjradeklarálás ugyanabban a blokkban

FogalomElfedés (shadowing)

Egy belső blokkban deklarálhatunk a külsővel azonos nevű változót: ettől a ponttól a blokk végéig a belső elfedi a külsőt. A belső deklaráció előtt a blokkban még a külső látszik! A blokk után újra a külső látszik.

int x;  std::cin >> x;
if ( x > 0 )
{
  std::cout << x;  // a külső x
  int x = 2;       // innentől a belső x
  ++x;             // a belsőt növeli
}
++x;               // újra a külső

dia: „Azonos nevű változók”

A dián a kód mellett soronként jelölve, melyik x látszik.

FogalomGlobális változó

Függvényeken kívül deklarált változó: a deklarációtól a fájl végéig minden függvényből látszik. Statikus tárterületen van, a program indulásakor jön létre, és ha nincs kezdőérték, nullára inicializálódik (a lokális nem!). Kerüljük: bárhonnan módosítható, nehéz követni.

dia: „Globális változók”

int x;
int y;
void f() { int i = 0; ++i; }
void g() { int i = x; int j = x + y; }
Fogalomextern és static globális szinten
  • int x; (globálisan) – definíció: itt jön létre a változó; más fordítási egységből is elérhető.
  • extern int y; – csak deklaráció: „van valahol (másik fájlban) egy int y”. A linker köti össze a definícióval.
  • static int s; – belső szerkesztésű: csak ebben a fordítási egységben látszik; másik fájlban lehet ugyanilyen nevű, nem ütköznek.

Ha két fájl is definiálja ugyanazt a globális nevet, linkelési hiba (multiple definition).

extern int y;
static int s;

{
  int q;
}
EszközHatókör-feloldó operátor ::

::x mindig a globális x-et jelenti, akkor is, ha egy lokális x elfedi. A::x az A névtér x-e, std::cout az std névtér cout-ja. (Lokálisan elfedett külső lokális változót viszont nem lehet elérni.)

dia: „Globális/lokális”

int x = 0;
void f()
{
  int x = 1;
  if ( x > 0 )
  {
    int x = 2;
    ++x;
    ::x = x;
  }
  ++x;
}
FogalomNévtér (namespace)

Nevek csoportosítása a névütközések elkerülésére: A::x és B::x két külön változó. C-ben nincs névtér. A linker számára a fordító a névteret belekódolja a szimbólumnévbe (name mangling): A::x → _ZN1A1xE (az nm paranccsal látható).

dia: „Névterek C vs C++”

namespace A { int x; } // A::x
namespace B { int x; } // B::x
$ nm ns.o
0000000000000000 B _ZN1A1xE
0000000000000004 B _ZN1B1xE
PéldaNévtérbeli függvény definíciója kívül

void A::f() { ++x; } a névtéren kívül van leírva, de a törzsében a nevek keresése az A névtérben kezdődik: ezért ++x az A::x-et növeli, nem a globális x-et.

dia: „Névtér”

int x;
namespace A
{
  int x;
  void f();
}
void A::f()
{
  ++x;   // A::x
}
FogalomMemóriaszegmensek
  • végrehajtási verem (stack): lokális változók, függvényparaméterek, visszatérési címek;
  • statikus tárterület: globális és statikus változók, a szövegliterálok ("Hello");
  • kódszegmens: maga a lefordított program;
  • heap (szabad tár): new-val / malloc-kal futás közben foglalt memória.

dia: „Memória szegmensek”

FogalomVégrehajtási verem

Minden függvényhíváskor egy stack frame (aktivációs rekord) kerül a verem tetejére: paraméterek, lokális változók, visszatérési cím. Visszatéréskor lekerül. A verem tetejét az SP (stack pointer), a keret alját a BP (base pointer) regiszter jelzi (ESP/EBP 32, RSP/RBP 64 biten). Előny: nagyon gyors, automatikus felszabadítás. Korlát: kicsi (néhány MB), és az élettartam a blokkhoz kötött. A hívási láncot a hibakereső stack trace-ként mutatja.

dia: „Végrehajtási verem működése”

  • Stack frame, aktivációs rekord
  • BP, SP, EBP, ESP, RBP, RSP
  • Függvényhívások
  • Előnyök
  • Limitációk
CsapdaStack overflow

Ha a rekurziónak nincs megállási feltétele, minden hívás újabb keretet tesz a veremre, míg az el nem fogy: „Segmentation fault (core dumped)”. Javítás: if ( n <= 1 ) return 1;.

dia: „Stack overflow”

int fac( int n )
{
  return n * fac( n - 1 );
}
int main()
{
  fac( 3 );
}
Segmentation fault (core dumped)
FogalomDinamikus memóriakezelés

Ha a verem kevés, vagy az objektumnak túl kell élnie a blokkot, a heap-en foglalunk. C-ben malloc/free, C++-ban new/delete. Párosítás szigorúan:

  • int* p = new int( i ); → delete p; (egy int, kezdőértéke i)
  • int* q = new int[ i ]; → delete [] q; (i elemű tömb)

new[]-ra sima delete (vagy fordítva) nem definiált viselkedés. Csak szükség esetén használjuk.

dia: „Dinamikus memóriakezelés C++-ban”

void f( int i )
{
  int *p = new int( i );
  // ...
  delete p;
}
void g( int i )
{
  int *q = new int[ i ];
  // ...
  delete [] q;
}
CsapdaMemóriakezelési hibák
  • memóriaszivárgás (memory leak): a lefoglalt memóriát nem szabadítjuk fel (pl. kivétel miatt nem ér el a vezérlés a delete-ig);
  • dupla felszabadítás (double free): kétszer hívunk delete-et ugyanarra (akár két különböző pointeren át);
  • lógó pointer (dangling pointer): a pointer már felszabadított memóriára mutat, és használjuk.

C++-ban nincs szemétgyűjtés (garbage collection). A hibák felderítésére: valgrind.

dia: „Dinamikus memóriakezelés”

  • Heap szerepe
  • malloc, new, new []
  • free, delete, delete []
  • Problémák: Memória-szivárgás, memory leak; Dupla free; Dangling pointerek
  • Garbage collection
  • valgrind (demo)
  • Szükség esetén használjuk
SzabályTípus és tárolási hely független

Hogy valami a veremre vagy a heapre kerül, az nem a típusától függ, hanem attól, hogyan hozzuk létre: beépített típusú adat is lehet a heapen (new int), és felhasználói típusú objektum is a vermen (complex c( 1.2, 3.4 );). A heapre a verem korlátai miatt (méret, élettartam) teszünk dolgokat.

dia: „Mi kerül a heapre?”

  • Stack limitáció
  • Alaptípus/beépített típusú adatot tárolhatunk a heap-en
  • Felhasználói típusú objektumot tárolhatunk a stack-en
  • Független kérdés: típus és memória
FogalomRAII

Resource Acquisition Is Initialization: az erőforrást (memória, fájl, zár) egy osztályba csomagoljuk; a konstruktor megszerzi, a destruktor felszabadítja. Ha az objektum lokális változó, a destruktor automatikusan lefut, amikor a vezérlés elhagyja a blokkot, akár kivétellel is, így nincs szivárgás. Pl. std::vector<int> v( i ); a new int[ i ] + delete [] helyett.

dia: „RAII”

  • Erőforrás, resource
  • C++: csomagoljuk be ezeket egy osztályba
  • Konstruktor, destruktor
  • Használunk saját típusú lokális változó objektumokat
  • Élettartam szabályok
  • Stroustrup: „C++ is a resource-oriented programming language.”
  • Resource acquisition is initialization
void f( int i )
{
  std::vector<int> v( i );
  // ...
}

SzabályAutomatikus változók

A blokkban deklarált (nem static) változó a veremen él: akkor jön létre, amikor a vezérlés eléri a deklarációt, és megszűnik, amikor elhagyja a blokkot. Ha egy függvény többször hívódik, minden híváskor új példány születik. Pl. egy if blokkban létrehozott std::vector<int> x a blokk végén megszűnik, a destruktora felszabadítja a memóriát.

  • Megszűnnek: a vezérlés elhagyja a deklaráló blokkot
SzabályLokális statikus változók

static int x = 1; egy függvényben: csak a függvényben látszik, de egyszer jön létre (amikor a vezérlés először eléri; ekkor inicializálódik), és a program végéig él, megőrzi az értékét a hívások között. Így f(); f(); először 1-et, aztán 2-t ír ki.

SzabályGlobális, névtérbeli változók és osztály statikus tagjai

Ezek a statikus tárterületen vannak: a program indulásakor (még a main előtt) jönnek létre, és a program végén szűnnek meg. Osztály statikus tagja (static const char* filename;) az osztályhoz tartozik, nem az egyes objektumokhoz: egy példány van belőle.

SzabályTemporálisok (ideiglenes objektumok)

Kifejezés kiértékelésekor névtelen köztes eredmények keletkeznek: e = a + b + c + d; esetén a + b, majd (a + b) + c … (pl. Matrix vagy std::string típusnál ezek valódi objektumok). Egy temporális a (rész)kifejezés kiértékelésekor jön létre, és a teljes kifejezés végén (a ;-nél) megszűnik.

Csapdaconst char* p = (h + w).c_str(); – a h + w temporális string a sor végén megszűnik, p lógó pointer lesz.

dia: „Temporálisok”

  • Létrejönnek: a (rész)kifejezés kiértékelésekor
  • Megszűnnek: a teljes kifejezés kiértékelésének végén
std::string h = "Hello";
std::string w = "World";
const char* p = (h + w).c_str();
std::cout << p;
CsapdaLokális változó címének visszaadása

Az answer függvény egy lokális tömb címét adja vissza; a tömb a függvény végén megszűnik, a hívó lógó pointert kap (a g++ figyelmeztet: „address of local variable returned”). Megoldások és gondjaik: globális vagy static tömb (működik, de minden hívás ugyanazt a tömböt írja felül); new char[ 80 ] (a hívónak kell delete []-elni, különben szivárog); a hívó adja a puffert (helyes, de kényelmetlen). A jó megoldás: std::string-et visszaadni érték szerint.

dia: „Feladat / Implementáció”

char* answer( const char* question )
{
  std::cout << question << std::endl;
  char ans[ 80 ];
  std::cin.getline( ans, sizeof( ans ) );
  return ans;
}

FogalomVisszatérés érték szerint: RVO és move

Ha egy függvény std::string-et ad vissza érték szerint, a jelentés tiszta (a hívó saját objektumot kap, nincs lógó pointer és szivárgás). Félhetnénk, hogy a másolás drága, de a fordító RVO-val (return value optimization) a visszaadott objektumot közvetlenül a hívó helyén hozza létre, ha pedig mégsem, C++11 óta mozgatás (move) történik: csak a belső pointer költözik át, a karakterek nem másolódnak.
